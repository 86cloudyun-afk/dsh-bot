# v1.1 模板、任务依赖与责任交接

状态：按用户授权实施，最终以 PR 复审与原生验收结果交付。全局约束见 [总规格](2026-10-09-v1.1-native-upgrade-design.md)。

## 1. Bot 与团队模板

模板为随插件提供的角色配方，不是 DSH 原生 preset。提供个人助理、资料整理、开发、测试四种 Bot 配方，及“资料整理与复核”“开发与测试”两种团队配方。角色、名称和分工可在创建前修改；模型从当前官方目录选择，默认沿用 DSH。不得创建硬编码供应商凭据或要求不存在的模型。

Bot 模板包含 templateId、templateVersion、名称／说明、role、建议名称、executionMode，及可选的原生 presetId。团队为 1–15 个唯一 roleKey、对应 Bot 配方、协调者 roleKey 和群设置；群轮数 1–3，请求预算 1–60。现有普通 Bot／群创建继续可用。

`template.list` 为只读。`template.instantiate` 为 human-only 写操作，必须携带 operationId、expectedRevision、templateId、templateVersion、每个角色的明确创建配置及可选群名。先验证全部角色的 cwd、contact／execution、preset 和参数，再在一次事务中创建全新 Bots 与普通内部群。回执返回 botIdsByRole、groupId；同一个原始请求返回原 IDs。

模板不复制工具白名单、权限／共享策略、凭据、已有会话、记忆、任务或执行状态。创建模板实例不启动会话或模型。任何一个角色配置无效，全队零创建。

入口放在 Bots 创建表单及协作的内部群创建表单，无新增主导航。

## 2. 任务依赖

使用 `task.dependsOn: taskId[]`，旧任务默认为 `[]`。它是业务先后关系，区别于已有 `origins` 和 readDependencies 的信息来源。直接依赖最多 30 个，不允许重复、自己依赖自己或全图环；跨 Bot、归档任务同样参与图校验。

`task.create` 可选 dependsOn。`task.dependencies.set` 必须带 taskId、expectedVersion、dependsOn，要求当前任务控制与每项前置任务的读取权限。修改只能在任务及相关工作真实结算后进行，递增 version 与既有 definitionVersion，验收回到 unknown。目标、验收条件、标题或依赖改变属于定义变化；归档／恢复、交接及同一定义的验收记录变化不改变定义。

`task.start` 在保留槽位前检查每项前置条件：

1. 当前 acceptance 为 passed，且证据绑定当前 definitionVersion／定义摘要。
2. 当前被验收尝试属于该定义，确切 attemptId／epoch 匹配，真实资源已结算。
3. 原结果／报告和验收证据可读，调用者与即将执行的负责 Bot 均具有读取权限。

返回结果而未验收、failed／unknown、旧定义验收、held UNKNOWN 均不得解锁。归档不会单独使同一定义的有效验收失效。缺少新证据字段的旧版验收不可推断成有效，需对已结算真实尝试明确重新记录验收。

阻塞任务不占槽、不启动原生工作；任务卡显示具体“等待依赖验收”原因。没有自动级联启动；前置通过后普通开始按钮可用，定时任务也必须执行相同准入检查。

准入时持久保存 `attempt.prerequisiteInputs`：前置 taskId、观察 version、definitionVersion／摘要、验收 attemptId／epoch、证据与来源、实际保存的结果／报告引用。记录实际内容的 provenance 到执行 binding。已开始工作使用固定输入，上游后续修改不改写／重启／假装停止它；下次尝试检查最新条件。授权撤销仍阻止后续请求、工具和结果发布，已消费内容与真实资源结算保持历史。

## 3. 责任交接

新增 `task.handoff`，所属任务控制者可发起，接收 Bot 需要相应控制授权，输入为 taskId、expectedVersion、toBotId、note（最多 2000 字符）。接收 Bot 必须 active；先完成所有验证，再改变当前负责人。

- 本任务没有持槽尝试，包括 starting／running／stopping／UNKNOWN。
- 关联子工作无持槽或未知结果；子任务的父尝试也已真实结算。
- 没有会被重新解释的 queued／admitting／UNKNOWN 原结果投递。
- 接收 Bot 有权读取既有任务内容、来源与接续必需证据。

用户先停止在途尝试，再等待结算，停止接受回执不能代替结算。成功只改变当前 task.botId、递增一次 version、追加 handoff 历史；保留 taskId、定义、原验收、epoch、createdBy、source、originSessionId、旧 attempts／Session bindings／reports／outbox 身份。

交接记录包含原 operationId、fromBotId、toBotId、真实调用者来源、note、时间、previousAttemptId、beforeVersion／afterVersion 和 provenance。丢回执后的同 ID 接续只有一条记录。交接不启动工作、不转移记忆或授权、不改旧投递目标；下次明确开始才使用接收 Bot 的执行模型与槽位。

`task.adjust(botId)` 使用同一授权与 settled-only 交接入口，不能作为旧 API 绕过边界。纯交接不改变 definitionVersion 或同一定义验收；同时改目标／条件／标题则在同一事务中按定义变更失效验收。未通过验证时零修改。旧执行日志仍按原 Bot 身份与原来源权限读取，不能因负责人变更放宽旧日志共享。

## 4. 模块接口与验收

新增模板 controller；复用 BotDirectory 的原生配置验证与已验证配置的同步入账函数，复用既有群创建事务逻辑。任务扩展在 TaskController 与 PermissionPolicy 中完成，依赖／交接不新建工作执行引擎。新接口在 commands／service 暴露明确字段、权限与版本。

必须覆盖：

- 不可用模型、无效参数／目录、坏 preset、团队重复角色和未知字段使团队创建整体失败；重放原请求返回完全相同 IDs。
- 模板创建零会话／模型／授权／记忆复制，DSH 工具审批默认可用。
- 自环及跨 Bot 两／三节点环、并发依赖修改、撤销来源读取，失败零槽／零原生工作。
- 同定义通过验收解锁；仅操作版本变化不阻塞；旧定义、返回未验收、UNKNOWN 不解锁。
- 上游变化不改已准入输入；新尝试重新检查。源权限撤销后实际请求／工具／发布被封住，但不伪造结算。
- running／stopping／UNKNOWN、未结算父子和未知投递均拒绝交接，旧 adjust 不能绕过。
- 成功交接全部旧 ID／验收／日志身份保留，重试一次记录，新尝试用新 Bot 配置；旧停止和迟到提交不影响新尝试。
- 15 槽、一级子工作、会议行动任务、原生审批、冷读、恢复回归继续通过。

已准入的前置内容同时保存为不可变 taskInputs，引用使用 taskInput 身份；读取按原 taskId／Bot 的当前共享上限、原执行会话及原内容来源检查，不把上游后续新增的私有来源误加到已消费内容。回执重放和 snapshot 发布仍重新核验这些引用。
