# Single Bot work-session contract

This slice adds a private owner-facing work contract. It is not the final DSH Bot GUI or autonomous native execution. The final delivery still requires an actual interactive plugin main conversation, independent work sessions, live state/results and stop controls.

An existing retained owner can call `Host.openOwnedWorkSessionPort(caller, {botId,botEpoch,authorityEpoch,isCurrent?})`. The frozen port exposes `delegate`, `query`, `createSession`, `queueMessage`, `admit`, `collect`, `fence`, `resume`, `spawnChild` and `dispose`. It does not expose the owner capability, Host, Ledger or runtime. The small native-controller `workPort` wrapper retains real fiber/controller lifetime; its development-native dependencies remain unavailable in the stock installation.

`delegate` requires `task_id`, `goal`, and `completion_condition`. The key is `[botId,task_id]`; same instructions return stable internal taskId, reserved sessionId and generation. Changed instructions conflict. Default delegation reserves a Session ID. The explicit creation bridge described below creates that original ID through the existing SessionCreationDriver; the synthetic execution runtime keeps its separate creationState evidence. Query is synchronous even while synthetic start or receipt lookup is unresolved.

Mutations use existing command envelopes with native-owner authorization, expected nativeOwner/Bot/task epochs, work revision, operationId/nonce/digest and root instruction reference. Exact cached receipts remain historical; stale generation/fence or owner/configuration changes reject replay. A new delegation operation can obtain the current mapping without duplicating work. No serialized actor or runtime label grants authority.

The default runtime returns `unsupported_work_generation_receipts` on admission, leaves the identity queued/reserved and invokes no creation/start API. The installed official Session API has create/adopt, cold reads, prompt acceptance and cancellation acceptance, but no product generation-addressed settlement/suspension proof. Cancellation retains queued inbox work; accepted cancellation cannot free a slot.

An optional constructor-only `OfflineWorkSessionRuntime` is an explicit synthetic seam. All of its results say `offline-synthetic`; they do not prove autonomous-model or stock-native operation. Receipts must come from the originally retained runtime instance and match exact task/Session/generation/admission operation, source, sequence and digest. SourceId is only a label. A fresh Host can query durable identities/count reservations, but cannot adopt or settle a prior Host's runtime-bound generation by copying receipt fields. Cross-instance recovery returns `work_source_continuity_unsupported`.

The ledger shares 15 potentially executing work slots per Bot across every port. Admission reserves before runtime invocation; duplicates never reserve twice. Main/contact is separate. Each reservation carries a `slotLease` tuple `{taskId,sessionId,generation,operationId}`. Confirmed quiescent waiting/terminal receipts release only that exact generation. A delayed generation-1 release cannot release generation-2's slot. Unknown work and unconfirmed stop remain held. Known legacy execution uncertainty blocks admission; native coverage beyond this owner ledger is not claimed.

`fence` locally prevents future work/result publication; it is not confirmed native stop. Exact source settlement may release a fenced old reservation without changing its result to completed. `resume` requires confirmed nonexecuting waiting, retains task/Session identity, increments generation and requires a new admission. Cross-owner handoff is unsupported. `spawnChild` returns `child_spawn_unsupported`; internal depth policy permits several first-level children within the same budget and rejects recursion, but actual child execution is absent.

`collect` performs at most one pending lookup per task/generation and returns within a 2000 ms timer bound for asynchronous sources even when AbortSignal is ignored. A timed-out lookup is quarantined; repeated calls cannot accumulate unresolved source requests. Timeout/rejection never establishes settlement. This is not preemption of synchronously blocking JavaScript.

The plugin GUI currently registers `src/client/client.js` through `window.__ModuleLoader__`, mounts the `main` and `sidebar.panellist` slots, and uses only `ctx.connection.rpc.call('/dsh-bot','snapshot',{},signal)`. Host `src/plugin.mjs` accepts only snapshot; execute refuses. The standalone `ui/` local-token/CLI management path is not the final interactive plugin delivery and must not become the Bot authority path.

The explicit private `dsh-bot/bot-producer` export now provides `installOwnedBotProducer`. It requires the exact owner Context/fiber, Host capability and live contact Agent/Session for the selected Bot. It retains these objects and configuration/authority epochs. The capability exposes `delegate`, `query`, `queue` and `dispose`; no RPC, UI or production startup binds it. Its scoped `dsh_bot_delegate` tool accepts only task_id, goal and completion_condition. A ToolRuntime agent/callId/token is provenance, not independent authority: execution must match the retained origin Agent and live owner.

Creation uses owner-only `creation:{cwd,port}` or synchronous `creation:{cwd,portFor}` options. The factory receives a frozen copy of the committed original intent, is consumed once even on failure, and retains exact returned methods. Durable adapters flush the actual Session and read its original JSONL header, empty event list and effective mounted preset/tool scope. Only the exact verified stock adapter port can mark `sessionCreation.proofKind='stock-session-durable'`; copied/wrapped ports and fixture labels remain `fixture-contract`. Historical created evidence survives later queued messages and generation2 reuse; a pending old-generation result cannot bind the new generation. The separate legacy `creationState` from synthetic runtime receipts cannot establish or erase this proof.

`queue` constructs one identified official UserMessage from the immutable work goal and completion condition. Its source has kind `dsh-bot`, retained producer/Bot/origin identity, ingress, task/target/generation/operation, and tool call IDs when applicable. The stock SDK separates protocol role from producer identity: role `user` represents external input, while source `dsh-bot` truthfully identifies its Bot producer. No human source or configured-human actor is substituted.

Delivery calls the exact retained idle, tool-free target Agent's `send(message,'next-turn',false)`, then flushes and cold-reads the original message. Prepared/sending/unknown intent states retain the final message identity. A send or flush ambiguity never causes resend or wake; subsequent attempts only inspect the original message. Authority, origin, target, method and generation changes prevent late success. `durably-queued` proves a historical inbox insertion, not present pending membership, model execution, settlement, current quiescence, or lease release. It remains a historical receipt if a later inbox event removes that message.

The offline acceptance fixture uses actual rc.2 Controller, Agent, SessionStore, JSONL backend, Query and ToolRuntime. Its LLM is a counted throwing fixture; synthetic tool invocations and narrowly declared fault/replacement shims are not model-selected delegation. Native execution is never invoked. Independent cold queries run with no Agent service, and a reopened product Ledger restores only identity evidence, not producer authority.

Remaining connection work needs a native generation-addressed execution and settlement contract (including ambiguous dispatch recovery, exact generation stop/quiescence and lease release). Stock whole-Agent whenIdle and cancellation acceptance do not provide it; fixed development NativeRunHost targets do not admit dynamic replacement. UI action authorization remains pending, and no read-only OperatorPeer is promoted. Current nativeRuntimeVerified and releaseReady remain false.
